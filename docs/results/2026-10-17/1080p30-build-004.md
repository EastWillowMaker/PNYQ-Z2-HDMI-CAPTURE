# 1080p30 build004: incorrect serializer clock relationship

The fresh build used immutable source `029c403` under
`artifacts/1080p30-source-004` and output `artifacts/1080p30-loop-004`.
It passed HLS, BD validation, IP synthesis, top synthesis and routing. Vivado
generated an internal `capture_wrapper.bit`, but the strict final check rejected
critical child-run diagnostics and exported no deployable bit/HWH/manifest pair.
The board was not reconfigured.

The repeated diagnostic was:

```text
CRITICAL WARNING: [Timing 38-249] Generated clock capture_i/hdmi_out_tx/U0/SerialClk has no logical paths from master clock hdmi_test_clock_pixel_clk.
```

The pinned IP's `src/rgb2dvi_clocks.xdc` declares SerialClk as five times PixelClk.
This fixture instead supplies both clocks externally. Its MMCM/BUFIO serial
branch is371.25MHz; a BUFR divide-by-five supplies74.25MHz PixelClk. There is no
physical PixelClk-to-SerialClk path. The incorrect constraint overrides the
otherwise propagated MMCM clock at the serializer port.

The diagnostic loop opened the unchanged routed004 checkpoint and exported its
timing constraints. A candidate removed exactly that generated-clock command.
After resetting and reloading the candidate constraints, the serializer's
SerialClk carried `mmcm_clk`, period2.694ns, master `clk_fpga_0`; PixelClk retained
the related13.468ns clock. No Timing38-249 or critical log diagnostic occurred.
Raw evidence is under `artifacts/operator/hdmi-xdc-checkpoint-probe-003*`;
`probe-hdmi-xdc-checkpoint.tcl` and the original/candidate exported XDC files are
preserved beside it. The original004 output remains unchanged.

The corrected-checkpoint reports showed setup0.539ns and hold0.013ns, zero
failing timing endpoints, all56reported bus-skew paths MET, and no unsafe or
unknown CDC endpoints in the reported clock crossings. A fresh standalone
methodology report contained warnings only. The timing summary had been
generated before that fresh methodology run and embeds the old cached
TIMING-36 finding; its explicit stale-report note must be considered. The
standalone fresh report, rather than the cached table, establishes that the
incorrect generated-clock finding disappeared in this probe.

Remaining reported warnings include LUT-driven asynchronous resets, a
suboptimally placed receiver reset synchronizer, CDC recognition and missing
external DDC/HPD delays. Reported CDC safety does not prove physical input/output
timing or every reset scenario. The probe is a diagnosis of the clock model;
it is not a new implementation build or permission to deploy004.

Commit `7935b71` removes only that command from the isolated copied IP, checks
the fixture's external-clock configuration and binds the adapted XDC SHA256
in the source/build manifests. It rejects unexpected pinned source contents.
Pristine vendor files, OOC constraints and serializer RTL are unchanged. Focused
mode/build/HWH tests passed47; full host tests passed574 with one optional
Migen/LiteX module skipped. A new full build005 must pass the existing strict
checks before deployment. No false path, clock waiver or severity reduction was
added.
