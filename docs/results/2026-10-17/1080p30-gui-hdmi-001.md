# Real HDMI desktop save verification

The actual Tk desktop viewer received the physical J9→J10 HDMI loop through
the uninstrumented cfd30d3 sender on port9043. The local harness waited for
three received frames, invoked the real save button and automated only the
file dialog. Its freeze-method wrapper retained the exact selected complete
frame for comparison; it did not supply a separate capture reader or image.

The [result](1080p30-gui-hdmi-001.json) passed:

- Saved image1920×1080,24bits/pixel, BMP compression code0.
- Decoded RGB888 exactly matched all6,220,800received bytes at button time.
- Both RGB hashes were
  `bc1653e4bc4345c7b36b634eb6df10a313de5382a2d7064c8e64e608da40ab2b`.
- Independent analytic pattern verification passed every byte and all1080
  optical marker rows for source ID1766; no mixed frame or pixel mismatch.

The viewer closed normally after saving. The
[board sender](1080p30-gui-hdmi-001-board.json) ended normally after its bounded
30seconds, exit0, DMA safe and zero source/cleanup/network errors. It retained
the previously documented ignored PYNQ UIO destructor warning after safe
teardown. The selected transport frame ID was10, distinct from optical ID1766.

The harness is `artifacts/operator/check-board-gui-hdmi-001.py`; raw host/board
logs are `artifacts/operator/1080p-gui-001-*`. The actual BMP, sidecar and result
remain local in `artifacts/operator/board-gui-hdmi-001/`; no image was committed
or uploaded. This verifies the actual GUI save path and pixel contract, not
every interactive preference, display arrangement or disk failure scenario.
